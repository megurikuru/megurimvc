## はじめに

本書は、前作『.NET on Debian で 同人活動に優しい SNSの開発【基礎編】』（C104初版・2025年12月第2版）の続編にあたる一冊です。

ただ、タイトルに「機能編」とは付けませんでした。実装した機能をカタログのように並べるのではなく、**なぜこのSNSを育て続けているのか、基礎編から何をどう変えてきたのか、そしてどんな場を目指しているのか**を、コードと設計判断の両面から綴る「読み物＋技術エッセイ」にしたかったからです。

同人ソフトや個人開発が好きなエンジニアの方には、`.NET 10` や `ASP.NET Core MVC`、画像最適化やタグのシソーラス設計といった技術的なこだわりを楽しんでいただければ嬉しいです。そして同時に、絵を描く人・小説を書く人だけでなく、**「趣味や『好き』を穏やかに眺めたり、少しだけ語ったりしたい人」**にも開かれた場として `meguri` を知ってもらい、読み終えたあとにふらっと覗いてみたくなる——そんな一冊を目指しました。

## 第1章：基礎編から今へ — 「好きがめぐる」場を育て続ける理由

### 1.1 基礎編で掲げた3つの原理原則

C104で頒布した『基礎編』では、同人活動に優しいSNSをつくるための土台として、大きく3つの原理原則を掲げました。

1. **規制よりもゾーニング**
   表現を一律に禁止・排除するのではなく、見る側が「見たいものを選び、見たくないものを避けられる」仕組みで棲み分ける。
2. **オールジャンル対応**
   イラスト・マンガ・小説といった創作ジャンルだけでなく、ゲーム・音楽・クルマ・IT・日常の趣味まで、どんな「好き」でも居場所をつくれる構造にする。
3. **数字競争よりも交流主体**
   インプレッションやバズを競うアルゴリズムではなく、同じ興味を持つ人同士が落ち着いてやり取りできる場にする。

これらは、開発を始めた当初の「こういう場所があったらいいな」という素朴な願いから生まれたものでした。

### 1.2 作り続けるうちに見えてきた「場の輪郭」

基礎編のあと、実際に手を動かして画面を作り、自分で触り、試行錯誤を重ねていくうちに、`meguri` が目指す空気感の輪郭がよりはっきりと見えてきました。

- **出会い系にしない**
  属性やマッチングを前面に出すのではなく、あくまで「界隈」「タグ」「投稿」といった**話題や創作・趣味そのもの**を起点につながる。
- **強い否定的リアクションを避ける**
  SNSが疲れる大きな原因のひとつは、攻撃的な反応や「反対・低評価」の数字が目に入ることです。`meguri` では、創作や語りに対して温かい反応や「読んだよ」の足あとが自然に届く設計を選びました。
- **見る・読む・語るだけの人も気楽にいられる**
  「同人活動に優しい」と言うと、つい「作品を発表するクリエイターだけの場所」に見えがちです。けれど、同人文化や趣味の世界を支えているのは、読む人、観る人、感想をぽつりと落とす人、静かに眺める人たちでもあります。作品を作らなくても、ただ好きなものの話題を眺めて気楽にいられる場所でありたい——その思いが今の設計に強く反映されています。

### 1.3 なぜ「機能編」ではなく、今の物語を書くのか

もし本書を「機能編」として書いていたら、「投稿機能の実装」「コメント機能の実装」「DM機能の実装」といった手順書になっていたと思います。しかし、生成AIの進化によって「仕様が決まっていればコードを書くこと自体」のハードルは大きく下がりました。

今の時代に本当に価値があるのは、コードの書き方そのもの以上に、**「なぜその機能を入れ、なぜ別の機能を入れなかったのか」「どういう空気感を守りたくて、このデータ構造や言葉遣いを選んだのか」**という設計思想の記録です。

だからこそ本書では、基礎編からの変化をたどりながら、`meguri` という小さなSNSの現在地をありのままお伝えすることにしました。

## 第2章：基礎編の実装からどう変わったか — アーキテクチャと設計の進化

### 2.1 「外部依存を減らしつつ、無理のないコストで回す」

個人開発のSNSでいちばん大切なのは、華やかなマイクロサービス構成ではなく、**ひとりで無理なく維持し続けられること**です。

`meguri` では基礎編から一貫して、「必要なものは標準機能とシンプルな構成で賄い、外部サービスは本当に効くところにだけ使う」というスタンスを継承しています。フロントエンドも大規模なSPAフレームワークや複雑なビルドパイプラインには載せず、**ASP.NET Core MVC（Razor View）＋ Vanilla JS ＋ 素のCSS** で構成しています。

### 2.2 インフラ・構成の現在地

現在の `meguri` は、以下のようなシンプルで堅実な構成で動いています。

```text
[ ブラウザ ]
	 │ HTTPS
	 ▼
[ Apache2 (リバースプロキシ / Debian 12 on AWS EC2) ]
	 │ HTTP (127.0.0.1:5000 / ForwardedHeaders)
	 ▼
[ Kestrel (ASP.NET Core MVC / .NET 10) ]
	 ├──▶ [ PostgreSQL ]       （ユーザー・界隈・投稿・タグ・メタデータ）
	 ├──▶ [ Cloudflare R2 ]    （WebP最適化済みの画像バイナリ）
	 ├──▶ [ SMTP (MailKit) ]   （メール確認・パスワードリセット等）
	 └──▶ [ Cloudflare Turnstile ] （ボット対策）
```

主なポイントは以下のとおりです。

- **ランタイムの進化**：ターゲットフレームワークは `.NET 10`（`net10.0`）。最新の ASP.NET Core Identity（`IdentitySchemaVersions.Version3`）を採用し、パスワード認証に加えて **パスキー（WebAuthn）** や **2要素認証（TOTP）** にも対応しています。
- **リバースプロキシとIPレート制限**：Apache2 の後ろで Kestrel を `127.0.0.1:5000` で待ち受け、`app.UseForwardedHeaders()` で実クライアントIPを受け取ります。その上で .NET 標準の `AddRateLimiter` を使い、一般アクセス・パスワードログイン・パスキー認証のそれぞれにIP単位のレート制限をかけています。
- **メール運用**：`MailKit` を用いた自前の `EmailSender` で SMTP 送信を行い、設定は `appsettings.json` の `SMTPServerConf` セクションに集約しています。
- **デプロイのシンプルさ**：デプロイスクリプト（`publish.sh`）もわずか数行です。

```sh
systemctl stop kestrel-meguri-fans.service

dotnet publish --configuration Release
rm -rf /var/www/meguri-fans
cp -pr /home/meguri/repos/megurimvc/Meguri/bin/Release/net10.0/publish /var/www/meguri-fans
chown -R www-data:www-data /var/www/meguri-fans

systemctl start kestrel-meguri-fans.service
```

「止めて、ビルドして、差し替えて、起動する」。個人運営のフェーズでは、この見通しの良さがトラブル時の復旧の速さに直結します。

### 2.3 画像の扱い方の進化 — DB格納・Base64から、SkiaSharp＋WebP＋R2へ

基礎編からの大きな進化のひとつが、画像の扱い方です。

基礎編では実装のシンプルさを優先して画像をDBに格納し、Base64で表示するアプローチを採っていました。しかし、実際に画像を複数枚添付する投稿やコメントが増えてくると、DB容量の肥大化やページ応答の重さ、キャッシュの効かせづらさが課題になります。

現在の `meguri` では、画像のアップロードから配信までを次の3段階で設計しています。

1. **検証・リサイズ・WebP最適化（`ImageProcessingService`）**
   - 受け取り上限は 5MB（JPEG / PNG）。拡張子だけでなく **Magic Bytes（ファイルシグネチャ）** を検査し、`SkiaSharp` で実際にデコードして破損や不正ヘッダーを弾きます。
   - ポスターや高解像度イラストも受け入れられるよう最大許可解像度は `32768px` まで広げつつ、保存前に長辺 `2048px` 以内へリサイズ（Mitchell 補間）し、**250KB 以下の WebP** へ自動最適化します。
   - Linux（Debian 12）環境でのネイティブ依存トラブルを避けるため、`SkiaSharp.NativeAssets.Linux.NoDependencies` を採用しています。

2. **オブジェクトストレージへの分離（`R2StorageService`）**
   - DB（`Images` テーブル）には `StorageKey`・`Width`・`Height`・`FileSize`・`Alt`・`Figcaption` といったメタデータのみを保存し、バイナリ本体は **Cloudflare R2**（`AWSSDK.S3` の S3 互換クライアント）に格納します。

3. **コントローラー経由のゾーニング付き配信（`ImageController`）**
   - R2 のバケットをそのまま公開 URL にせず、`/Image/File/{id}` を通じて配信しています。
   - 理由は明確で、**画像の公開範囲・R-18・R-18G のゾーニングを「親の投稿・コメント・メッセージ」に厳密に追従させるため**です。

```csharp
// Meguri/Controllers/ImageController.cs（抜粋）
bool PostVisible(Post p) =>
	(p.IsPublic || isAuthenticated) &&
	(!p.IsSexual || showSexual) &&
	(!p.IsViolence || showViolence);

// 公開かつ全年齢の投稿に紐づく画像のみ public キャッシュを許可
Response.Headers["Cache-Control"] = cacheable
	? "public, max-age=86400"
	: "private, no-cache";
```

「画像URLだけ直リンクされたらゾーニングをすり抜けてしまう」という穴を塞ぎつつ、全年齢・公開画像には適切な `Cache-Control` を付与して表示の快適さも両立しています。

### 2.4 `megurikuru/megurimvc` の設計とコード整理

公開リポジトリ `megurikuru/megurimvc` では、ASP.NET Core MVC の王道構造をベースに、役割ごとに見通しよく整理しています。

```text
Meguri/
├── Controllers/   # 機能単位のコントローラー（Fandom, Post, Tag, Image, Message, Reaction 等）
├── Models/        # EF Core エンティティ（Post, Fandom, TagConcept, Tag, TagRelationship 等）
├── ViewModels/    # 画面専用の ViewModel（Account, Fandom, Post, Tag, Manage, Shared 等）
├── Services/      # 業務ロジック・外部連携（ImageProcessing, R2Storage, Tag, Email, Turnstile）
├── Validation/    # 独自バリデーション（頻出パスワード拒否・パスフレーズ長検証など）
├── Resources/     # 多言語リソース（SharedResource.ja.resx / SharedResource.en.resx）
├── Data/          # ApplicationDbContext, DbInitializer, TestDataSeeder
├── Views/         # Razor ビューと再利用パーシャル（_Finder, _PostItem, _ReactionButtons 等）
└── wwwroot/
	├── css/meguri/ # base / layout / parts / page / pc に分割した素の CSS
	└── js/meguri/  # reactions / tag-manager / image-viewer 等、機能別 Vanilla JS
```

特に意識しているのは次の3点です。

- **エンティティと画面モデルの分離**：`Models/` をそのままビューに渡さず、`ViewModels/` に画面ごとの表示・入力モデルを切り出すことで、過剰なバインディングやビューの肥大化を防いでいます。
- **CSSとJSの「小さく分ける」設計**：フレームワークに頼らない代わりに、`wwwroot/css/meguri/parts/` や `wwwroot/js/meguri/` に機能単位で細かくファイルを分割し、どこを直せばどの画面に効くかを追いやすくしています。
- **多言語対応の土台づくり**：文言は `SharedResource.ja.resx` / `SharedResource.en.resx` に集約し、Identity のエラーメッセージも `LocalizedIdentityErrorDescriber` で日本語化しています。

## 第3章：「優しい空気感」をつくるUXと言葉遣いの工夫

### 3.1 「技術で何ができるか」ではなく「どう心地よく過ごせるか」から逆算する

SNSの空気感は、規約の文章だけで決まるものではありません。ボタンのラベル、リアクションの種類、タイムラインの見せ方、初期設定のデフォルト値——そうした細部の積み重ねが、「ここではこう振る舞うのが自然だ」という空気をつくります。

たとえば `meguri` の投稿に対するリアクション（`ReactionType`）は、次の8種類に絞っています。

| 種類 | アイコン | ニュアンス |
| --- | :---: | --- |
| `Like` | ❤️ | すき / いいね |
| `Emotional` | 😭 | 泣けた / エモい |
| `Bravo` | 👏 | すごい / 拍手 |
| `Insight` | 💡 | なるほど（納得・理解） |
| `Impressed` | 🧐 | ほぅ（興味・感銘・関心） |
| `Seen` | 👀 | 読了 / 見たよ（足あと） |
| `Thinking` | 🤔 | 考えさせられる（深考・考察） |
| `Lol` | 😂 | 草 / ｗｗ（ユーモア・ギャグ） |

ここには「怒り」や「低評価（Bad）」のような強い否定的リアクションを置いていません。代わりに、`👀 読了 / 見たよ` のような「感想を言語化するほどではないけれど、ちゃんと読んだよ」とそっと伝えられるリアクションを用意しています。書く人にとっても、読むだけの人にとっても、心理的なハードルを下げるための選択です。

また、トップページの新着一覧（`_PostItem`）では `ShowStats = false` として、一覧上でリアクション数やコメント数の数字を前面に出しすぎないようにしています。「数字が大きい投稿が偉い」という空気をなるべく作らないための小さな配慮です。

### 3.2 「入る」「入ってる」「出る」という軽やかな表現

コミュニティ機能は、言葉遣いひとつで重さが変わります。

「入会」「加盟」「退会」といった硬い言葉は、ちょっとした興味で覗いてみたい人にとって心理的な壁になりがちです。そこで `meguri` では、界隈（Fandom）との関わり方を**「入る」「入ってる」「出る」**といった、普段の会話に近い軽やかな感覚で捉えられるように設計しています。

実際に画面上のラベルでも、参加済みの状態には「入ってる」「入ってる界隈」といった柔らかい日本語を採用しています。同好会に正式入会するのではなく、**イベントの島や部室をふらっと覗いて、気が向いたらそこに居て、別の興味が湧いたらまた移動する**——そんな気負わない距離感を大切にしています。

### 3.3 「界隈」と「タグ」で『好き』を巡らせる仕組み

`meguri` で話題や「好き」が巡る軸は、**「界隈（Fandom）」**と**「タグ（Tag）」**の2本立てです。

- **界隈（階層ツリー構造）**
  `Fandom` モデルは `ParentFandomId` による自己参照の親子構造を持ちます。パンくずリストとファインダー風のUI（`_Finder.cshtml`）によって、「創作 ＞ イラスト」「趣味 ＞ クルマ ＞ メーカー別」のように階層をたどりながら、自分の居場所を探せます。
- **タグ（シソーラス構造）**
  単純な文字列タグではなく、**概念（`TagConcept`）**・**各言語の表記（`Tag`）**・**概念同士の関係（`TagRelationship`：`broader` 上位語 / `related` 関連語）** に分けて設計しています。さらに同名の別概念を案内する曖昧さ回避（`Disambiguation`）の仕組みも備えています。

```text
[ TagConcept (概念) ]
   ├── 1 : N ──▶ [ Tag ] （日本語/英語、代表表記・同義語・正規化文字列）
   └── N : N ──▶ [ TagRelationship ] （上位語 broader / 関連語 related）
```

表記ゆれや言語の違い、関連ジャンル同士のつながりを吸収できる構造にしておくことで、ひとつの「好き」から隣の「好き」へと自然に視界が広がっていきます。

### 3.4 外部SNS連携に頼らない考え方と、安心感・ルール設計

多くのWebサービスでは「Googleでログイン」「Xでログイン」といった外部SNS連携が当たり前になっています。しかし、外部プラットフォームの仕様変更やアカウント凍結に巻き込まれるリスク、あるいは「普段のアカウントとは切り離して静かに趣味を楽しみたい」というニーズを考えると、外部SNSへの依存は必ずしも安心につながりません。

そこで `meguri` では、**自前の認証基盤（ASP.NET Core Identity）をしっかり作り込む**道を選びました。

- メール確認を必須としつつ、パスワードポリシーは「複雑な記号の強制」ではなく **12〜128文字のパスフレーズ重視**（＋頻出パスワードを拒否する `CommonPasswordValidator`）を採用。
- パスワードレスで安全にログインできる **パスキー（Passkey）** や **2要素認証（2FA）** をサポート。
- ゾーニング設定として、生年月日による18歳以上判定（`IsAdult()`）に加え、ユーザー自身が「性的な投稿（R-18）を表示するか（`ShowSexual`）」「暴力表現を含む投稿（R-18G）を表示するか（`ShowViolence`）」を明示的に切り替えられるようにしています。デフォルトはもちろんオフ（非表示）です。

「見たくないものを勝手に見せられない」「外部アカウントと紐づけずに自分のペースで使える」——この2つが、穏やかな場を支える土台になっています。

## 第4章：個人開発・バイブコーディングのリアル

### 4.1 手を動かして形にしていく面白さ

個人開発のいちばんの醍醐味は、「こうしたらもっと気持ちよく使えるのでは？」と思いついたアイデアを、その日のうちに画面やコードとして形にできることです。

近年はAIエディタやコーディング支援ツールと対話しながら進める、いわゆる**バイブコーディング**的な開発スタイルも大きな味方になりました。定型的なCRUDやViewModelの配線、CSSの細かな調整、多言語リソースの追加といった作業を高速に回せるようになったことで、開発者自身が**「体験の設計」や「本当に欲しい仕様の見極め」**に時間を使えるようになったのは大きな変化です。

### 4.2 迷ったこと、作り直したこと、細部を詰める過程

もちろん、最初からきれいに一直線に進んだわけではありません。リポジトリのコードや構成の端々にも、試行錯誤の跡が残っています。

- **画像まわりの見直し**
  最初は手軽にDB格納から始めましたが、複数枚添付（最大16枚）やポスター級の高解像度画像、さらには JavaScript 無効時のサイズ超過エラー返却まで考慮するうちに、Kestrel のリクエストサイズ上限拡張、Magic Bytes チェック、SkiaSharp での 250KB WebP 最適化、Cloudflare R2 への移行、そして `ImageController` でのアクセス制御へと段階的に作り直しました。
- **CSSとUIパーツの整理**
  最初は1枚にまとまっていたスタイルも、ページが増えるにつれて見通しが悪くなり、`base.css`・`layout.css`・`parts/*.css`・`page/*.css`・`pc.css` という構成に整理し直しました。アイコンも軽量な SVG を自前で配置し、ボタンやフォーム、パンくず、ページネーションの細かな余白や手触りを何度も微調整しています。
- **認証とセキュリティの現実解**
  DB初期化後に古い認証Cookieが残る問題に対処するため `SecurityStampValidatorOptions` の検証間隔を詰めたり、パスワードスプレー攻撃やパスキーエンドポイントへのDoSに備えてレート制限をエンドポイント単位で分けたりと、実際に運用を見据えるほど「地味だけど大事なコード」が増えていきました。

AIに丸投げするだけでは、こうした「自分のサービスの空気感や運用条件に合った判断」は出てきません。AIのスピードを借りつつも、**最後の違和感に気づいて直すのは、実際にサービスを触り続ける人間の役割**だと実感しています。

### 4.3 開発中だからこそ大切にしている、正直な運用スタンス

個人開発のSNSを運営していると、「いつまで続くのか」「データは大丈夫なのか」という不安をユーザーに与えてしまいがちです。そこで `meguri` では、格好をつけて完璧な永続性を約束するのではなく、利用規約（`_TermsContent.cshtml`）にも正直に次のように明記しています。

> 本サービスは現在開発中であり、運営者は、事前の通知なく本サービスの内容を変更し、または提供を停止・終了することができるものとします。また、開発および運用上の都合により、事前の通知なくデータを消去する場合があります。

また、開発環境でのリセットやテストデータ投入を安全かつ再現性高く行えるよう、`DbInitializer` や `TestDataSeeder` も整備しています。

「まだ育てている途中の場であること」を隠さずに伝えることで、運営側も無理をして燃え尽きずに済みますし、使う側も「実験的で穏やかな新しい場」として気楽に付き合える——それもまた、個人開発SNSを長く続けるための大切な工夫だと考えています。
