## はじめに

本書は、『.NET on Debian で 同人活動に優しい SNSの開発【基礎編】』（C104 2024年8月12日初版）の続編にあたります。

当初は基礎編に続く「機能編」にしようと思っていたのですが、基礎編を書いたころとは違ってAIによるコーディング支援が当たり前になり、紙面を使って長いサンプルコードを載せる価値は以前よりも下がっています。ソースコードの全文は GitHub（`https://github.com/megurikuru/megurimvc`）でいつでも見られるからこそ、本書ではコードの書き方そのものよりも、「なぜこのSNSを開発しているのか」「基礎編のころからどう変わってきたのか」「どのような場を目指しているのか」という物語と設計の意図に重きを置くことにしました。

とはいえ、SkiaSharp による WebP 最適化や Cloudflare R2 を使ったゾーニング連動配信、タグのシソーラス設計、レート制限・認証まわりの工夫といった要点については、構成図やコードの抜粋も交えながら紹介しています。`meguri` の開発に興味がある方はもちろん、個人開発でSNSやWebサービスをつくってみたい方の参考になれば幸いです。

本書を読んで気になったら、ぜひ `https://meguri.fans/` をふらっと覗いてみてください。

## 第1章：基礎編から今へ — 「好きがめぐる」場を開発する理由

### 1.1 基礎編（C104）で掲げた3つの原理原則

C104で頒布した『基礎編』では、同人活動に優しいSNSをつくるための土台として、大きく3つの原理原則を掲げました。

1. **規制よりもゾーニング**  
2. **短文投稿、動画投稿、イラスト投稿などの個別ジャンル対応ではなく、オールジャンル対応**  
3. **フォロワー数やいいねの数を競うことよりも、ユーザーの間の交流が主体の場**  

これらは、既存のSNS、主に、X（旧Twitter）や、Pixivを使っていて、こうだったらいいなと感じていた部分です。

### 1.2 つくりながら見えてきた「場の輪郭」

実際に機能や画面をつくりながら試行錯誤を重ねていくうちに、`meguri` が目指す輪郭がある程度は明確になってきました。

- **見たい情報を自分で選べるようにする**  
  SNSでは「興味のない情報や見たくない投稿が勝手に流れてくる」ことがストレスになりがちです。`meguri` では、界隈（Fandom）やタグ、ゾーニング設定を通じて、ユーザーが自分の意思で見たい情報を選べる場を目指しています。
- **強い否定的リアクションを避ける**  
  議論や批評が必要な場も世の中にはありますが、趣味や「好き」を持ち寄る場では、そこまで批評精神を持ち込まなくてもいいのかなと思っています。創作や語りに対して、温かい反応や緩い反応が届きやすい設計を心がけています。
- **見る・読む・語るだけの人も気楽にいられる**  
  「同人活動に優しいSNS」と聞くとクリエイター向けの印象が先行しがちですが、同人文化や趣味の世界を支えているのはつくり手だけではありません。作品を読む人、イベントで本を手に取る人、感想をぽつりと落とす人、静かに眺めるだけの人も大切な参加者です。作品を発表しなくても居場所がある——そんな「見る専・読む専・語る専」にとっても気楽な場でありたいという思いが、今のUIや機能設計に反映されています。

> **コラム：`meguri` という名前に込めた思い**
>
> 同人誌即売会の会場を歩いていると、スペースに立つサークル参加者も、カタログを片手に島をめぐる一般参加者も、みんな同じ「好き」でつながっていることに気づきます。`meguri` という名前には、誰かの「好き」が別の誰かの「好き」へと穏やかにめぐっていく場所であってほしい、という願いを込めました。

## 第2章：基礎編の実装からどう変わったか — アーキテクチャと設計の進化

### 2.1 「外部依存を減らしつつ、無理のないコストで回す」

個人開発でSNSを運用し続けるうえで、いちばん現実的な敵は「高すぎるインフラ費用」と「複雑すぎて自分がメンテできなくなる構成」です。

多数のユーザーを抱える大規模サービスなら、複雑なシステム構成も必要でしょう。しかし、ひとりで設計・実装・運用・同人誌執筆まで回す個人開発では、構成要素が増えるほど「久しぶりに触ったら動かなくなっていた」「月額コストがじわじわ効いてくる」という事態に陥りかねません。

そこで `meguri` では基礎編から一貫して、次の基本スタンスを貫いています。

- **基本は単一の ASP.NET Core MVC アプリケーションで完結させる**
- **フロントエンドは Razor View ＋ Vanilla JS ＋ 素のCSS（ビルドツール不要）**
- **外部サービスは「自前で持つと苦しいところ」にだけピンポイントで採用する**

### 2.2 インフラ・構成の現在地

現在の `meguri` は、AWS EC2 上の Debian 12 を土台に、次のようなシンプルで堅実な構成で稼働しています。

```text
[ ユーザーのブラウザ ]
		  │ HTTPS (443)
		  ▼
[ Apache2 (リバースプロキシ / Debian 12 on AWS EC2) ]
		  │ HTTP (127.0.0.1:5000 / X-Forwarded-For 等)
		  ▼
[ Kestrel (ASP.NET Core MVC / .NET 10) ]
		  ├──▶ [ PostgreSQL ]           ユーザー・界隈・投稿・タグ・画像メタデータ
		  ├──▶ [ Cloudflare R2 ]        WebP最適化済みの画像バイナリ
		  ├──▶ [ SMTP (MailKit) ]       メール確認・パスワードリセット・登録済み通知
		  └──▶ [ Cloudflare Turnstile ] 新規登録・ログイン等のボット対策
```

基礎編の時点からの進化・現在地を比較表にまとめると、以下のようになります。

| 領域 | 基礎編のころ | 現在の `meguri`（`megurimvc`） |
| --- | --- | --- |
| ランタイム | .NET 8 | `.NET 10` |
| DB | PostgreSQL | 変わらず |
| 認証 | パスワード + 2FA | パスキー（推奨）・ パスワード + 2FA|
| 画像保存 | DB格納・Base64表示 | SkiaSharp で WebP 250KB最適化 → Cloudflare R2 格納 |
| 画像配信 | HTML内にインライン展開 | `/Image/File/{id}` 経由でゾーニング＆キャッシュ制御 |
| 防御 | なし | .NET標準 `AddRateLimiter`（用途別IP制限）＋ Cloudflare Turnstile |

#### リバースプロキシと用途別レート制限

Apache2 の背後で Kestrel を `127.0.0.1:5000` で待ち受ける構成では、そのままではアプリ側に見える接続元IPがすべて `127.0.0.1` になってしまいます。`Program.cs` では `UseRouting()` の前に `app.UseForwardedHeaders()` を配置し、`appsettings.json` の `ForwardedHeaders:KnownProxies` に `127.0.0.1` と `::1` を明示することで、正しいクライアントIPを取得しています。

そのうえで、.NET 標準の `AddRateLimiter` を使い、次の3系統でレート制限を分けています。

1. **一般アクセス（`IpRateLimiting`）**：短時間に異常な回数のリクエストを送るIPを一定時間ブロック（`429 Too Many Requests` ＋ `Retry-After` ヘッダー返却）。
2. **パスワードログイン（`PasswordLoginRateLimiting`）**：5分間に10回まで。パスワードスプレーや辞書攻撃を抑制。
3. **パスキー認証・登録（`PasskeyRateLimiting`）**：5分間に20回まで（1回の操作で Options 取得と検証の2通信が走るため、ログインより少し余裕を持たせている）。

外部のWAFや高価なミドルウェアに頼らなくても、.NET 標準機能と設定ファイルだけでここまで手堅く組めるのは、ASP.NET Core の大きな魅力です。

#### デプロイのシンプルさ（`publish.sh`）

本番反映用のスクリプト `publish.sh` は以下のようなシンプルな内容です。デプロイのたびに「止めて、ビルドして、差し替えて、起動する」だけで済むので、個人運営でも安心感があります。

```sh
systemctl stop kestrel-meguri-fans.service

dotnet publish --configuration Release
rm -rf /var/www/meguri-fans
cp -pr /home/meguri/repos/megurimvc/Meguri/bin/Release/net10.0/publish /var/www/meguri-fans
chown -R www-data:www-data /var/www/meguri-fans

systemctl start kestrel-meguri-fans.service
```

### 2.3 メール運用とアカウント列挙対策

SNS運用で意外とハマりやすいのがメール送信です。`meguri` では `MailKit` を使った自前の `EmailSender`（`IAppEmailSender`）を実装し、`SMTPServerConf` から接続先・ポート・認証情報を読み込んで SSL 接続で送信しています。

ここで地味にこだわっていることが2点あります。

1. **プレーンテキストメールを選ぶ**
   装飾過多なHTMLメールではなく、`new TextPart("plain")` でシンプルなテキストメールを送っています。メーラーごとの崩れを気にする必要がなく、スパム判定も受けにくく、確認リンクやリセットコードも素直に読めます。
2. **登録済みメールアドレスの列挙を防ぐ（`SendAlreadyRegisteredNoticeAsync`）**
   新規登録フォームにすでに登録済みのメールアドレスが入力されたとき、画面上で「このメールアドレスはすでに使われています」と返してしまうと、第三者が「誰が登録しているか」を探る手がかり（アカウント列挙）になってしまいます。そこで、`EmailSender` に `SendAlreadyRegisteredNoticeAsync` を用意し、画面上は通常の確認案内と同様に振る舞いつつ、該当メールアドレスの持ち主へ「すでに登録されています（ログイン・パスワード再設定はこちら）」と静かに通知する設計にしています。

### 2.4 画像の扱い方の進化 — DB格納・Base64から、SkiaSharp＋WebP＋R2へ

基礎編からの実装面で最も大きく進化したのが、画像の扱い方です。

基礎編では「まずは動くものをシンプルにつくる」ことを優先して画像をDBに格納し、Base64で表示するアプローチを採っていました。数枚のテスト画像であればこれで十分動きます。しかし、実際にSNSとして複数枚の画像を投稿やコメントに添付できるようになると、「PostgreSQLのバックアップが肥大化する」「Base64埋め込みでHTML応答が重くなりキャッシュも効かない」「最大16枚添付時に帯域を圧迫する」といった課題が一気に見えてきます。

現在の `meguri` では、画像のアップロードから保存、配信までを次の3段階に分離しています。

#### ① 検証・リサイズ・250KB以下WebP最適化（`ImageProcessingService`）

- **入力制限と Magic Bytes 検査**：1ファイル最大 5MB、拡張子は `.jpg` / `.jpeg` / `.png` のみ許可。さらに拡張子偽装を防ぐため、先頭バイトのシグネチャ（JPEG: `FF D8 FF`、PNG: `89 50 4E 47 0D 0A 1A 0A`）を検証します。
- **SkiaSharp によるデコード＆高解像度対応**：実際に `SKBitmap.Decode` を通すことで壊れたファイルや不正なヘッダーを弾きます。同人イベントのポスターや高解像度イラストもアップロードできるよう、最大許可解像度は `8192px` から **`32768px`** へ拡張しました。
- **初回リサイズと段階的WebP圧縮**：長辺が `2048px` を超える場合は Mitchell 補間でリサイズしたうえで、品質を `85 → 75 → 65 → 55 → 45 → 35 → 25` と段階的に下げながら **250KB 以下** を目指して WebP エンコードします。それでも250KBを超える場合は解像度を `0.8` 倍ずつ縮小して確実に目標サイズ内へ収めます。

```csharp
// Meguri/Services/ImageProcessingService.cs（抜粋）
int[] qualityLevels = new[] { 85, 75, 65, 55, 45, 35, 25 };

foreach (var quality in qualityLevels) {
	cancellationToken.ThrowIfCancellationRequested();
	lastResult = EncodeWebp(image, quality);
	if (lastResult.Length <= TargetMaxOutputSizeBytes) {
		return (lastResult, image);
	}
}

// 品質25でも250KBを超える場合は段階的に解像度を縮小
while (lastResult.Length > TargetMaxOutputSizeBytes && (image.Width > 320 && image.Height > 320)) {
	var resized = ResizeBitmap(image, (int)(image.Width * 0.8), (int)(image.Height * 0.8));
	image.Dispose();
	image = resized;
	lastResult = EncodeWebp(image, 40);
	if (lastResult.Length <= TargetMaxOutputSizeBytes) {
		return (lastResult, image);
	}
}
```

Linux（Debian 12）環境でのネイティブ依存トラブルを避けるため、`SkiaSharp.NativeAssets.Linux.NoDependencies` を採用しているのも実運用上のポイントです。

#### ② Cloudflare R2 への分離格納（`R2StorageService`）

最適化された WebP バイナリは、S3 互換 API を持つ **Cloudflare R2** へ格納し、DB（`Images` テーブル）には `StorageKey`・`Width`・`Height`・`FileSize`・`Alt`・`Figcaption` といったメタデータのみを保存します。

#### ③ コントローラー経由のゾーニング付き配信（`ImageController`）

R2 のバケットをそのまま公開 URL にせず、あえて **`/Image/File/{id}` を通じて配信**しています。理由は明確で、**画像の公開範囲・R-18・R-18G のゾーニングを「親の投稿・コメント・メッセージ」に厳密に追従させるため**です。

```csharp
// Meguri/Controllers/ImageController.cs（抜粋）
bool PostVisible(Post p) =>
	(p.IsPublic || isAuthenticated) &&
	(!p.IsSexual || showSexual) &&
	(!p.IsViolence || showViolence);

// 公開かつ全年齢の投稿に紐づく画像のみ public キャッシュを許可
Response.Headers["Cache-Control"] = cacheable
	? "public, max-age=86400"
	: "private, no-cache";
```

「画像URLだけ直リンクされたらゾーニングをすり抜けてしまう」という穴を塞ぎつつ、全年齢・公開画像には適切な `Cache-Control` を付与して表示の快適さも両立しています。

### 2.5 `megurikuru/megurimvc` の設計とコード整理

公開リポジトリ `megurikuru/megurimvc` では、ASP.NET Core MVC の王道構造をベースに、個人開発でも迷子にならない見通しの良さを意識して整理しています。

```text
Meguri/
├── Controllers/    # 機能単位のコントローラー（Home, Fandom, Post, Tag, Image, Message, Reaction 等）
├── Models/         # EF Core エンティティ（ApplicationUser, Post, Fandom, TagConcept, Tag, Image 等）
├── ViewModels/     # 画面専用の入力・表示モデル（Account, Fandom, Post, Tag, Manage, Shared 等）
├── Services/       # 業務ロジック・外部連携（ImageProcessing, R2Storage, Tag, Email, Turnstile）
├── Validation/     # 独自バリデーション（CommonPasswordValidator, PasswordRequirementsAttribute 等）
├── Resources/      # 多言語リソース（SharedResource.ja.resx / SharedResource.en.resx）
├── Data/           # ApplicationDbContext, DbInitializer, TestDataSeeder
├── Views/          # Razor ビューと再利用パーシャル（_Finder, _PostItem, _ReactionButtons 等）
└── wwwroot/
	├── css/meguri/ # base / layout / parts/*.css / page/*.css / pc.css に分割した素の CSS
	├── js/meguri/  # reactions / tag-manager / image-viewer / image-attachment-manager 等
	└── icons/      # 自前配置の軽量 SVG アイコン群
```

設計・整理のうえで特に効いている工夫を3つ挙げます。

- **エンティティと画面モデルの分離**：`Models/` をそのままビューや POST アクションにバインドせず、`ViewModels/` に画面ごとのモデルを切り出すことで、過剰なバインディング（Over-posting）やビューの肥大化を防いでいます。
- **`ApplicationDbContext` での監査項目自動セット**：`SaveChanges` / `SaveChangesAsync` をオーバーライドし、`ApplyAuditFields()` で `CreatedAt` と `UpdatedAt` を一括設定しています。コントローラー側での更新日時セット忘れを仕組みでなくす小さな工夫です。
- **ビルド不要のフロントエンド分割と多言語化の土台**：フレームワークに頼らない代わりに、`wwwroot/css/meguri/parts/` や `wwwroot/js/meguri/` に機能単位で細かくファイルを分割し、どこを直せばどの画面に効くかを追いやすくしています。文言も `SharedResource.ja.resx` / `SharedResource.en.resx` に集約し、Identity のエラーメッセージも `LocalizedIdentityErrorDescriber` で自然な日本語に整えています。

## 第3章：「優しい空気感」をつくるUXと言葉遣いの工夫

### 3.1 「技術で何ができるか」ではなく「どう心地よく過ごせるか」から逆算する

SNSの空気感は、規約の文章だけで決まるものではありません。ボタンのラベル、リアクションの種類、タイムラインの見せ方、初期設定のデフォルト値——そうした日々の操作の中で目に入る細部の積み重ねが、「ここではこう振る舞うのが自然だ」という空気をつくります。

たとえば `meguri` の投稿・コメント・画像に対して画面上で押せるリアクションは、次の7種類にしています。

| 種類 | アイコン | ニュアンス |
| --- | :---: | --- |
| `Like` | ❤️ | 好き / いいね |
| `Emotional` | 😭 | 泣いた / 感動 |
| `Bravo` | 👏 | すごい / 拍手 |
| `Impressed` | 🧐 | ほぅ / 興味深い |
| `Seen` | 👀 | 見たよ |
| `Thinking` | 🤔 | ふ～ん / 考え中 |
| `Lol` | 😂 | 笑える / www |

ここには「怒り」や「低評価（Bad）」のような強い否定的リアクションを置いていません。代わりに、`👀 見たよ` のような**「感想を言語化するほどではないけれど、ちゃんと読んだよ」**とそっと伝えられるリアクションを用意しています。書く人にとっても、読むだけの人にとっても、心理的なハードルを下げるための選択です。

さらに実装面でも、細やかな配慮を入れています。

- **トップページ一覧での数字の抑制**：`Views/Home/Index.cshtml` から `_PostItem` を呼ぶ際、`ShowStats = false` を渡し、一覧上でリアクション数やコメント数の数字を前面に出しすぎないようにしています。「数字が大きい投稿が偉い」という空気をなるべく作らないための配慮です。
- **軽快で誤操作しにくいリアクションUI**：`wwwroot/js/meguri/reactions.js` では `Fetch API` で `/Reaction/Toggle` を非同期呼び出しし、通信中は同一ターゲットのボタンを一時的に無効化して連打による不整合を防いでいます。また、`aria-pressed` 属性も同時に更新しています。

### 3.2 「入る」「入ってる」「出る」という軽やかな表現

コミュニティ機能は、言葉遣いひとつで体験の「重さ」が大きく変わります。「入会」「メンバー登録」「脱退」といった管理システム的な硬い言葉が並んでいると、「ちょっと興味があるだけなのに大げさだな」「抜けたら気まずいかな」と足がすくんでしまいます。

そこで `meguri` では、界隈（Fandom）との関わり方を**「入る」「入ってる」「出る」**といった普段の会話に近い表現で統一し、画面上でも「入ってる界隈」などの柔らかい日本語を採用しています。堅苦しい会員制クラブではなく、**即売会の島や放課後の部室をふらっと覗いて、気が向いたらそこに居て、別の興味が湧いたら移動する**——そんな気負わない距離感を大切にしています。

### 3.3 「界隈」と「タグ」で『好き』を巡らせる仕組み

`meguri` で話題や「好き」が巡る軸は、**「界隈（Fandom）」**と**「タグ（Tag）」**の2本立てです。

#### 階層ツリーとしての「界隈」とファインダーUI

`Fandom` モデルは `ParentFandomId` による自己参照の親子構造を持ちます。画面上ではパンくずリスト（`_Breadcrumb.cshtml`）と、子界隈と投稿を並べて見渡せるファインダー風のUI（`_Finder.cshtml`）を組み合わせています。タイムラインが勝手に流れて消えてしまうSNSとは違い、「自分の手で棚をたどるように『好き』を探せる」感覚を大切にしました。

<!-- [スクショ配置：図3-2] 撮影対象: 界隈詳細ページ（パンくずリスト・参加/入ってる表示・子界隈と投稿のファインダー表示が見える画面） -->
![図3-2: パンくずリストとファインダー風UIで階層をたどれる「界隈」画面](images/fig3-2-fandom-finder.png)

#### シソーラス構造としての「タグ」と曖昧さ回避

オタク文化や趣味の世界では、同じものを指していても**表記ゆれ・略称・日本語と英語の違い**が頻繁に起きますし、逆に**同じ単語でもジャンルによってまったく別の意味になる（同音異義語）**ことも珍しくありません。

そこで `meguri` のタグは、単純な文字列ではなく**概念（`TagConcept`）**・**各言語の表記（`Tag`）**・**概念同士の関係（`TagRelationship`：`broader` 上位語 / `related` 関連語）**に分けたシソーラス構造で設計しています。

```text
[ TagConcept (概念) ]
   ├── 1 : N ──▶ [ Tag ] （日本語/英語、代表表記・同義語・正規化文字列）
   └── N : N ──▶ [ TagRelationship ] （上位語 broader / 関連語 related）
```

さらに `Views/Tag/Disambiguation.cshtml`（曖昧さ回避ページ）では、ひとつの概念に対して「同義語」「上位語」「下位語」「関連語」を整理できるようになっています。表記ゆれや言語の違いを吸収しつつ、関連語をたどって「まだ知らなかった隣の沼」へ自然に巡っていける仕組みです。

<!-- [スクショ配置：図3-3] 撮影対象: タグ詳細ページまたは曖昧さ回避ページ（同義語・上位語・下位語・関連語が見える画面） -->
![図3-3: 表記ゆれや関連ジャンルをつなぐタグのシソーラス・曖昧さ回避画面](images/fig3-3-tag-thesaurus.png)

なお、公開の場での交流（投稿・コメント）とは別に、1対1や複数人で落ち着いてやり取りできるメッセージ機能（`Conversation` / `ConversationMember` / `Message`）も備えていますが、こちらも「界隈や投稿で知り合った人と必要なときに話す」ための静かな補助線として位置づけています。

### 3.4 外部SNS連携に頼らない考え方と、安心感・ルール設計

多くのWebサービスでは「Googleでログイン」「Xでログイン」といった外部SNS連携が当たり前になっています。しかし、外部プラットフォームの仕様変更やアカウント凍結に巻き込まれるリスク、あるいは「普段のアカウントとは切り離して静かに趣味を楽しみたい」というニーズを考えると、外部SNSへの依存は必ずしも安心につながりません。

そこで `meguri` では、**自前の認証基盤（ASP.NET Core Identity）をしっかりつくり込む**道を選びました。

- **パスフレーズ重視のパスワード設計**：`appsettings.json` の `Identity:Password` では、複雑な記号や大文字・数字の強制ではなく **最小12文字〜最大128文字・異なる文字4文字以上**（`RequiredUniqueChars: 4`）を採用し、さらにユーザー名・メールアドレスの包含や頻出パスワードを拒否する `CommonPasswordValidator` を組み込んでいます。
- **パスキーと2要素認証**：パスワード管理の負担を減らしつつ安全性を高めるため、**パスキー（WebAuthn）** や **2要素認証（TOTP＋QRコード＋リカバリーコード）** を標準サポートしています。
- **年齢判定 × 明示的オプトインのゾーニング**：生年月日による18歳以上判定（`IsAdult()`）に加え、ユーザー自身が「性的な投稿（R-18）を表示するか（`ShowSexual`）」「暴力表現を含む投稿（R-18G）を表示するか（`ShowViolence`）」を明示的に切り替えられます。初期状態はいずれもオフ（`false`）であり、マイページの外部公開（`IsProfilePublic`）も初期値 `false` に設定しています。

![図3-4: ゾーニング表示設定やパスキー管理をまとめたアカウント設定画面](images/fig3-4-manage-options.png)

「見たくないものを勝手に見せられない」「外部アカウントと紐づけずに自分のペースで使える」——この2つが、穏やかな場を支える土台になっています。

## 第4章：個人開発・バイブコーディングのリアル

### 4.1 手を動かして形にしていく面白さと、バイブコーディングとの付き合い方

個人開発のいちばんの醍醐味は、「こうしたらもっと気持ちよく使えるのでは？」と思いついたアイデアを、その日のうちに画面やコードとして形にし、実際にブラウザで触って確かめられるところにあります。

最近の `meguri` 開発では、生成AIと対話しながら進める、いわゆる**バイブコーディング**的な開発スタイルも大きな味方になりました。実際に使ってみて感じたのは、AIが得意な領域と、人間が手放してはいけない領域がはっきり分かれているということです。

- **AIに任せて一気に進むこと**
  - ViewModel やパーシャルビューの雛形作成、多言語リソースキー（`.resx`）の整備
  - テストデータ投入（`TestDataSeeder`）やバリデーション属性の実装
  - JavaScript のイベント処理や非同期通信の安全な書き換え（連打防止・`aria` 属性付与など）
- **人間が握り続けるべきこと**
  - 「この機能は本当に `meguri` の空気感に合うか？」という引き算の判断
  - 画面を実際に触ったときの「ちょっとボタンが硬いな」「この余白は息苦しいな」という違和感の発見
  - ゾーニングやセキュリティ境界（画像配信・レート制限・アカウント列挙対策）の最終設計

AIは「言われた仕様を実装するスピード」を劇的に上げてくれますが、**「どんな場にしたいか」という美意識や責任までは代わりに持ってくれません**。AIのスピードを借りて実装の重労働を減らし、そのぶん浮いたエネルギーを「体験の細部を詰めること」に注ぐのが、個人開発における心地よい付き合い方かなと思います。

### 4.2 迷ったこと、つくり直したこと、細部を詰める過程

もちろん、最初からきれいに一直線に進んだわけではありません。リポジトリのコードや構成の端々にも、試行錯誤とつくり直しの跡が残っています。

- **画像複数枚添付（最大16枚）と「JS無効時」への備え**
  第2章で触れた画像パイプラインをつくり直す過程では、最大16枚の同時添付や JavaScript 無効時のサイズ超過エラー返却まで見据え、Kestrel と `FormOptions` のリクエストサイズ上限を `200MB` に拡張したうえで、個別ファイルのサイズ検証とエラーハンドリングを丁寧に組み直しました。
- **CSSの分割し直しと手触りの微調整**
  最初は1枚にまとまっていたスタイルシートも、ページが増えるにつれて見通しが悪くなり、機能・画面単位のファイル構成へ整理し直しました。ボタンやフォーム、パンくず、ページネーションの細かな余白や手触りも、実際に画面を触りながら何度も微調整しています。
- **運用を見据えて増えた「地味だけど大事なコード」**
  開発中にDBを初期化したあと古い認証Cookieが残る問題に対処するため、`SecurityStampValidatorOptions` の検証間隔を `TimeSpan.Zero` に設定し、リフレッシュ時にパスキー等の `amr` クレームが消えないよう `OnRefreshingPrincipal` で引き継ぎました。また、`TurnstileService` でも単に `Success == true` を見るだけでなく、`action` と `hostname` の一致および10秒タイムアウトまで検証しています。
