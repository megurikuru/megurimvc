当初は、基礎編に続くSNSとしての具体的な機能の実装を扱った「機能編」にしようと思っていたのですが、機能実装については、AIによるバイブコーディングに頼った部分が大きく、自身で把握しているコードが少ないままになってしまいました。そこで、機能の実装そのものよりも、**「なぜこのSNSを開発しているのか」「基礎編のころからどう変わってきたのか」「どのような場を目指しているのか」** という物語と設計の意図に重きを置くことにしました。

## 第1章：なぜこのSNSを開発しているのか — 「好きがめぐる」場の原点と輪郭

### 1.1 基礎編（C104）で掲げた3つの原則

C104で頒布した『基礎編』では、同人活動に優しいSNSをつくるための土台として、大きく3つの原則を掲げました。

1. **規制よりもゾーニング**  
2. **短文投稿、動画投稿、イラスト投稿などの個別ジャンル対応ではなく、オールジャンル対応**  
3. **フォロワー数やいいねの数を競うことよりも、ユーザーの間の交流が主体の場**  

これらは、既存のSNS——主にX（旧Twitter）やPixivを使っていて、「こうだったらいいな」と感じていた部分から生まれた原則です。

創作物や趣味の語りが、プラットフォーム側の急な方針変更や画一的な規制に振り回されることなく、かといって見たくない人の目にも無理やり飛び込んでいかないようにする。イラストだけ、小説だけ、短文だけ、と媒体ごとに分断されず、同じ「好き」の話題をひとつの場所でゆるやかに共有できる。そして、数字の競争ではなく、人と人との穏やかなやり取りが中心にある——それが [meguri](https://meguri.fans/) の出発点でした。

### 1.2 つくりながら見えてきた「場の輪郭」

基礎編の時点ではまだ抽象的な理念だった3つの原則も、実際に画面や機能をつくり、操作しながら試行錯誤を重ねていくうちに、meguriが目指す「場の輪郭」として少しずつ具体的になってきました。

- **見たい情報を自分で選べるようにする**  
  SNSを使っていて疲れやすい理由のひとつは、「興味のない話題や、今は見たくない投稿が勝手に流れてくること」だと思います。meguriでは、アルゴリズムに任せてタイムラインを流し続けるのではなく、**界隈（Fandom）** や **タグ**、そして **ゾーニング設定** を通じて、ユーザーが自分の意思で見たい情報へアクセスできる場を目指しています。
- **強い否定的リアクションを避ける**  
  議論や批評が必要な場も世の中にはありますが、趣味や「好き」を持ち寄る場所では、そこまで批評精神を前面に出さなくてもいいのではないかと思っています。創作や語りに対して、温かい反応や肩の力の抜けた反応が届きやすい空気を大切にしています。
- **見る・読む・語るだけの人も気楽にいられる**  
  「同人活動に優しいSNS」と聞くと、どうしても絵や小説を発表するクリエイター向けの印象が先行しがちです。けれど、同人文化や趣味の世界を支えているのはつくり手だけではありません。作品を読む人、イベントで本を手に取る人、感想をぽつりとつぶやく人、静かに眺めるだけの人も大切な参加者です。作品を発表しなくても居場所がある——そんな「見る人・読む人・語る人」にとっても気楽な場でありたいという思いが、現在の画面構成や機能設計に反映されています。

> **コラム：meguriという名前に込めた思い**
>
> 同人誌即売会の会場を歩いていると、スペースに立つサークル参加者も、カタログを片手に島をめぐる一般参加者も、みんな同じ「好き」でつながっていることに気づきます。meguriという名前には、誰かの「好き」が別の誰かの「好き」へと穏やかにめぐっていく場所であってほしい、という願いを込めました。

## 第2章：基礎編のころからどう変わってきたのか — 構成と機能の現在地

### 2.1 個人開発で回し続けるための基本スタンス

個人開発でSNSを運用し続けるうえで、いちばん現実的な壁は「インフラ費用」と「複雑すぎて自分がメンテできなくなる構成」です。

多数のユーザーを抱える大規模サービスであれば、分散構成やリッチなフロントエンド基盤も必要かもしれません。しかし、ひとりで設計・開発・運用まで回す個人サービスでは、構成要素が増えて目が届かなくなると、「久しぶりに確認したら動かなくなっていた」「クラウドの月額費用がとんでもないことなっていた」という事態に陥りかねません。

そこでmeguriでは、基礎編から一貫して次の基本スタンスを保っています。

- **基本は単一のASP.NET Core MVCアプリケーションで完結させる**
- **フロントエンドはRazorビュー ＋ 素のJavaScript ＋ 素のCSS（ビルドツール不要）**
- **外部サービスは「自前で持つと苦しいところ」にだけピンポイントで採用する**

機能がどれだけ増えても、土台のシンプルさはできるだけ崩さない。これが、基礎編から現在までの設計方針です。

### 2.2 インフラ・構成の進化と現在地

現在のmeguriは、AWS EC2上のDebian 12を土台に、次のようなシンプルな構成で稼働しています。

```text
[ ユーザーのブラウザ ]
          │ HTTPS (443)
          ▼
[ Apache2 (リバースプロキシ / Debian 12 on AWS EC2) ]
          │ HTTP (127.0.0.1:5000)
          ▼
[ Kestrel (ASP.NET Core MVC / .NET 10) ]
          ├──▶ [ PostgreSQL ]           ユーザー・界隈・投稿・タグ・画像メタデータ等
          ├──▶ [ Cloudflare R2 ]        WebP最適化済みの画像バイナリ
          ├──▶ [ SMTP (MailKit) ]       メール確認・パスワード再設定・登録済み通知
          └──▶ [ Cloudflare Turnstile ] 新規登録・ログイン等のボット対策
```

基礎編（C104）のころと現在のmeguri（megurimvc）を並べると、次のように変化しています。

| 領域 | 基礎編のころ（C104） | 現在のmeguri（megurimvc） |
| --- | --- | --- |
| ランタイム | .NET 8 | .NET 10 |
| データベース | PostgreSQL | PostgreSQL（変化なし） |
| 認証 | パスワード ＋ 2要素認証 | パスキー（推奨）・パスワード ＋ 2要素認証 |
| 画像保存 | DB格納 | WebP最適化（250KB） + Cloudflare R2格納 |
| 画像配信 | HTML内にインライン展開 | アプリ経由でゾーニング＆キャッシュ制御して配信 |
| 本文表現 | プレーンテキスト中心 | プレーンテキスト + Markdown（オプトイン方式） |
| 防御 | 特別な対策なし | .NET標準のレート制限（用途別）＋ Cloudflare Turnstile |
| 多言語対応 | 日本語のみ | 日本語・英語の切り替えに対応 |

本番環境への反映も、大がかりなCI/CDパイプラインを組むのではなく、次のようなシンプルなシェルスクリプトで「止めて、ビルドして、差し替えて、起動する」形にしています。個人開発では、いざというときに自分の手で仕組み全体を把握できることの安心感が何より大きいと感じています。

```sh
systemctl stop kestrel-meguri-fans.service

dotnet publish --configuration Release
rm -rf /var/www/meguri-fans
cp -pr /home/meguri/repos/megurimvc/Meguri/bin/Release/net10.0/publish /var/www/meguri-fans
chown -R www-data:www-data /var/www/meguri-fans

systemctl start kestrel-meguri-fans.service
```

### 2.3 「動く土台」から「SNSとして使える場」への変化

基礎編から現在までの間に、SNSとして実際に使ってもらうための機能がいくつも加わりました。細かなコードの実装はAIの力も借りながら進めていますが、 **「なぜその仕組みを選んだのか」** という設計の意図は私自身が決めたものです。ここでは、特に大きな変化のあった3つのポイントを紹介します。

#### ① 画像の扱い方の刷新 — DB格納・Base64から、WebP＋Cloudflare R2＋ゾーニング配信へ

基礎編では「まずは動くものをシンプルにつくる」ことを優先し、画像をデータベースにそのまま格納してBase64で表示する形を採っていました。数枚のテスト画像であれば十分動きますが、投稿やコメントに複数枚の画像（現在、投稿では最大16枚）を添付できるようになると、バックアップの肥大化やページ表示の重さ、通信量の圧迫が一気に現実的な問題になりえます。

そこで現在のmeguriでは、画像の扱いを以下のように変更しました。

- **受け取りと最適化**：1ファイル最大5MB（JPEG / PNG）を受け付け、拡張子だけでなくファイル先頭のデータ検証も通したうえで、高解像度のイラストやポスターも扱えるようにしつつWebP形式（250KB以下を目標）へ自動圧縮します。
- **保存先の分離**：画像バイナリ本体はS3互換の **Cloudflare R2** に預け、PostgreSQL側にはサイズや代替テキスト（Alt）・キャプションといったメタデータだけを持ちます。
- **ゾーニング連動の配信**：R2のURLをそのまま外部公開せず、あえてアプリ側（/Image/File/{id}）を経由して配信しています。これは、 **「画像の直リンクだけ共有されたらR-18 / R-18Gや界隈限定のゾーニングをすり抜けてしまう」** という抜け道を塞ぐためです。全年齢・公開の投稿に紐づく画像だけキャッシュを許可し、快適さと安全性の両立を図っています。

#### ② 表現の幅を広げるMarkdown対応

オールジャンル対応を掲げる以上、ひとこと感想のような短い文章から、イベントレポート、作品考察、小説、技術メモまで、さまざまな書き方を自然に受け止められるようにしたいと考えました。

そこで現在のmeguriでは、**投稿・コメント・メッセージ・自己紹介（Bio）** のそれぞれで、必要なときだけチェックを入れて使える **オプトイン方式のMarkdown対応** を取り入れています。

- ふだん通り気軽に書きたい人は、そのままプレーンテキストで投稿できる
- 見出し、リスト、引用、テーブル、コードブロック、タスクリスト、ルビ（振り仮名）などを使いたいときはMarkdownをオンにできる
- 編集画面にはツールバーとプレビュータブ、さらに自分のアップロード済み画像を選んで挿入できるピッカーを用意し、記法を暗記していなくても使えるようにする
- 変換後のHTMLはサーバー側で厳密にサニタイズし、安全に表現力を確保する

#### ③ 外部SNSに頼らない自前認証と、静かな防御

現在のWebサービスでは「Googleでログイン」「Xでログイン」といったソーシャルログイン機能を持つことが一般的ですが、外部プラットフォームの仕様変更や凍結に巻き込まれるリスク、あるいは「普段のアカウントとは切り離したい」という人もいるであろうことを考えて、ソーシャルログイン機能は外してもいいのではないかと考えました。

そこでmeguriでは、ASP.NET Core Identityを使って自前で認証を実装しています。さらに、次のような工夫で、ユーザーが安心して使えるようにしています。

- **パスキーの推奨**：パスワードを覚えたり使い回したりする負担を減らすため、端末の生体認証などでログインできるパスキーに対応しています。
- **パスフレーズ重視のパスワード設計と2要素認証**：パスワードを使う場合も、「大文字・記号必須」といった覚えにくいルールではなく、**12文字以上（最大128文字）の長さ**を重視し、ありがちなパスワードやユーザー名を含むものを弾く方針にしています。認証アプリによる2要素認証も使えます。
- **ボット対策と用途別レート制限**：新規登録やログインには **Cloudflare Turnstile** を組み合わせ、さらに.NET標準のレート制限機能を使って「通常アクセス」「パスワードログイン」「パスキー認証」の3系統で回数制限を設けています。
- **プレーンテキストメールとアカウント列挙対策**：確認メールやパスワード再設定メールは、崩れにくくスパム判定も受けにくいプレーンテキストで送信します。また、すでに登録済みのメールアドレスで新規登録が試みられた場合も、画面上で「登録済みです」と露出させず、持ち主のメール宛てに静かに案内を送る形にしています。

## 第3章：どのような場を目指しているのか — 穏やかな空気感をつくる設計の意図

### 3.1 数字を煽らず、緩くつながれるリアクション設計

SNSの空気感は、利用規約の文章で決まるものではありません。そもそも、利用規約を読む人の方が少ないですよね。ボタンのラベル、リアクションの種類、一覧画面の見せ方、初期設定のデフォルト値——そうした日々の操作の中で目に入る細部の積み重ねが、「ここではこう振る舞うのが自然だ」という空気をつくる要因になるのではないでしょうか。

たとえばmeguriで投稿やコメント、画像に押せるリアクションは、次の7種類にしています。

| 種類 | アイコン | ニュアンス |
| --- | :---: | --- |
| `Like` | ❤️ | すき・いいね |
| `Emotional` | 😭 | 泣いた・感動 |
| `Bravo` | 👏 | すごい・拍手 |
| `Impressed` | 🧐 | ほぅ（興味・関心） |
| `Seen` | 👀 | 見たよ（足あと） |
| `Thinking` | 🤔 | ふ～ん・考え中 |
| `Lol` | 😂 | 笑える・www |

ここには「怒り」や「低評価（Bad）」のような強い否定的リアクションを置いていません。代わりに、`👀 見たよ` のような**「感想を言葉にするほどではないけれど、ちゃんと読んだよ」**とそっと伝えられるリアクションを用意しています。書く人にとっても、読むだけの人にとっても、反応することの心理的なハードルを下げるための選択です。

また、トップページの新着投稿一覧では、リアクション数やコメント数といった数字を前面に出さないようにしています。「数字が大きい投稿ほど偉い」「バズっているものが正義」という空気をなるべく持ち込まないための工夫です。

### 3.2 「界隈」と「タグ」で『好き』を巡らせる設計

meguriで話題や「好き」が巡る軸は、**「界隈（Fandom）」** と **「タグ（Tag）」** の2本立てです。

#### 階層ツリーとしての「界隈」とファインダー風UI

「界隈」は親子の階層構造を持っており、画面上ではパンくずリストと、子界隈と投稿を並べて見渡せるファインダー風のUIを組み合わせています。タイムラインが勝手に流れて消えてしまうSNSとは違い、**「自分の手で本棚や即売会の島をたどるように『好き』を探せる」**感覚を大切にしました。

初期状態の界隈にも、`創作（イラスト・漫画等）`（イラスト／漫画／小説）だけでなく、`見る・読む（アニメ・漫画等）` や `ゲーム`、`コスプレ`、`音楽`、`アイドル`、`自動車`、`IT`、`社会`、`なんでも` といった幅広い入り口を用意しています。つくり手だけでなく、見る・読む・語る人も自然に居場所を見つけられるようにするためです。

#### シソーラス構造としての「タグ」と曖昧さ回避

オタク文化や趣味の世界では、同じものを指していても**表記ゆれ・略称・日本語と英語の違い**が頻繁に起きますし、逆に**同じ単語でもジャンルによってまったく別の意味になる（同音異義語）**ことも珍しくありません。

そこでmeguriのタグは、単純な文字列ではなく、**「概念（Concept）」**・**「各言語の表記（Tag）」**・**「概念同士の関係（上位語／下位語／関連語）」** に分けたシソーラス構造で設計しています。

```text
[ 概念 (TagConcept) ]
   ├── 1 : N ──▶ [ 表記 (Tag) ]（日本語/英語・代表表記・同義語）
   └── N : N ──▶ [ 関係 (TagRelationship) ]（上位語 / 下位語 / 関連語）
```

さらに「曖昧さ回避」ページを用意することで、ひとつの言葉が複数の意味を持つ場合も整理できるようになっています。表記ゆれや言語の壁を吸収しつつ、関連語をたどって「まだ知らなかった隣の沼」へ自然に巡っていける仕組みを目指しました。

#### 公開の場を支えるコメント・メッセージ・マイページ

投稿に対するコメントには、掲示板文化になじみ深い通し番号（`>>1`, `>>2`...）とツリー型の返信、画像添付を備え、削除されたコメントがあっても番号がずれて会話が壊れないようにしています。投稿自体も、タイトルだけ・本文だけ・画像だけでも出せる柔軟な形にしています。

また、公開の場での交流とは別に、1対1や複数人で落ち着いてやり取りできる **メッセージ機能** も備えています。

マイページ（プロフィール）では、アバターやヘッダー画像、自己紹介文、最大5件の外部URL（活動サイトや他SNSへのリンクなど）を置けるようにしており、同人活動の拠点案内としても使えるようにしています。

### 3.3 「規制よりもゾーニング」と安心感の設計

第1章で掲げた「規制よりもゾーニング」は、単なるスローガンではなく、ユーザー設定と公開範囲のデフォルト値にそのまま落とし込んでいます。

- **年齢判定 × 明示的オプトイン**：生年月日による18歳以上判定を行ったうえで、成人ユーザーであっても初期状態では「性的な投稿（R-18）」「暴力表現を含む投稿（R-18G）」はいずれも **非表示（オフ）** になっています。見たい人が自分で設定画面から明示的にオンにする仕組みです（18歳未満はチェック自体が無効になります）。
- **外部公開と界隈内限定の切り替え**：投稿ごとに「外部公開（未ログインでも閲覧可）」か「参加している界隈内での共有」かを選べるため、広く見てほしい告知と、界隈の中で落ち着いて話したい話題を自然に分けられます。
- **マイページの初期非公開**：プロフィールページの外部公開も、初期状態は **オフ（非公開）** です。「とりあえず登録して眺めるだけ」の人が、意図せず外部検索にさらされないようにするための配慮です。
- **日本語・英語の切り替え**：表示言語は設定画面から日本語・英語を切り替えられるようにしており、海外のファンやクリエイターがふらっと訪れる未来も視野に入れています。

## 第4章：バイブコーディングと個人開発のリアル — AIとつくって見えたこと

### 4.1 「機能編」から「設計思想の本」へ舵を切った理由

「はじめに」にも書いた通り、もともとC109では、基礎編に続く技術解説書として「機能編」を書くつもりでした。

ところが実際に開発を進めてみると、状況は基礎編のころとは大きく変わっていました。生成AIと対話しながら実装を進める、いわゆる**バイブコーディング**が、開発のスピードを劇的に変えてしまったのです。

画像のリサイズやWebP最適化、Cloudflare R2連携、タグのシソーラス構造、パスキー認証、Markdownエディタとサニタイズ、多言語リソースの整備——もしこれらをすべてひとりで調べ、ゼロから手書きしていたら、C109までに今の形へたどり着くのは難しかったと思います。AIのおかげで、「こういう場をつくりたい」というアイデアを、圧倒的な速さで実際に動く機能に変えることができました。

一方で、その裏返しとして **「動く機能はどんどん増えていくのに、コードの細部を自分の頭で完全に把握しきれていない」** という状況になりました。自分が理解していないコードを技術解説書にまとめるのはいかがなものか（AIに任せればそれも可能ですが）——そう感じたことが、「機能編」ではなく「物語と設計思想の本」へと舵を切った理由のひとつです。

### 4.2 AIに任せて進んだことと、人間が主導したこと

バイブコーディングを続けてみて実感したのは、AIが得意な領域と、現時点では人間が主導した方が良い領域がまだある（数か月先には分かりませんが）、ということでした。

- **AIの力で一気に進んだこと**
  - 画面のやビューモデルの基本実装、多言語リソースの整備
  - テストデータの生成や、各種バリデーション・エラーハンドリングの組み込み
  - JavaScriptによるインタラクション（リアクションの非同期通信、タグ入力補完、画像ビューア、Markdownエディタ等）の実装
- **人間が主導したこと**
  - **「この機能は本当にmeguriの空気感に合うか？」という判断**
  - **「ラベルの文言のチョイスがちょっと変」「この余白は息苦しいな」などの違和感の発見**
  - **ゾーニングや公開範囲、セキュリティの境界をどこに引くかという決定と責任**

AIは「言われた仕様を形にするスピード」を何倍にも引き上げてくれますが、**「どんな場にしたいか」という美意識や、運営者としての責任までは代わりに持ってくれません**。実装の重労働をAIに手伝ってもらい、そのぶん浮いたエネルギーを「場の輪郭を言葉にすること」「実際に操作して使い心地を確かめること」に注ぐ——それが、今回の開発における自分なりのAIとの付き合い方でした。

### 4.3 つくりながら迷ったこと、手触りを詰め続けたこと

AIの助けを借りたとはいえ、最初から一直線に完成したわけではありません。開発の履歴を振り返ると、むしろ「実際に操作してみて違和感に気づき、つくり直す」ことが多くありました。

- **複数枚画像添付と、うまくいかないケースへの備え**  
  最大16枚の画像をまとめて添付できるようにしたり、並び順を変えられるようにしたり、JavaScriptが動かない環境やサイズ超過時にも破綻しないようにリクエスト上限やエラー表示を見直したりと、地味なつくり直しを重ねました。
- **CSSの分割し直しと、画面の手触りの微調整**  
  最初はシンプルにまとまっていたスタイルシートも、ページが増えるにつれて見通しが悪くなり、パーツ単位・ページ単位へ整理し直しました。ボタンの押しやすさ、フォームの余白、フッターやヘッダーの収まり方、パスワード表示の切り替えなど、コミット履歴の大半はこうした細かなUI調整です。
- **運用を見据えた「目に見えない安心」の積み上げ**  
  ボット対策、レート制限のしきい値など、表の画面からは見えにくい部分ほど「あとから困らないように」と少しずつ手を入れ続けています。
